Two reasons a Windows machine could activate a licence and then refuse to
transcribe on the same connection minutes later.

## Certificates

The speech bridge is the one part of Pulpitry that runs on Node, and Node ships
its own list of certificate authorities and ignores the one Windows keeps.
Everything else here reads the system store.

So on a machine whose antivirus or church firewall inspects encrypted traffic —
which is most of them — the certificate doing the inspecting is trusted by
Windows, by every browser, and by the part of Pulpitry that activates your
licence. It was not trusted by the part that starts transcribing. That machine
would activate fine and then fail, and the message blamed the internet
connection.

Pulpitry now reads the same certificate store as the rest of the machine, where
the installed Node is new enough to be asked (22.15 or later).

## Proxies

Node reads neither the proxy Windows is configured with nor the registry it
lives in. On a filtered church or school network, every browser worked and the
bridge reached nothing.

Pulpitry now finds that setting and uses it — for both the subscription check
and the speech connection, which are separate connections and needed it
separately. If you have set `HTTPS_PROXY` yourself, that is used and nothing is
guessed.

## And it says what actually went wrong

The underlying error was being discarded, so anything that failed to connect
came out as "check the internet connection" — on the connection that had just
activated a licence. It now names the cause: a certificate that could not be
verified, a timeout, a name that would not resolve, a refusal.

If transcription still will not start, the message is worth reading and worth
sending to us.
